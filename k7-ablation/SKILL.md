# K7 Ablation：用证据做减法

把代码看成一组承担具体责任的机制。消融，就是暂时拿掉其中一个，观察用户结果、约束和成本发生了什么变化，再决定它是否值得留下。

目标是让读者需要理解的概念更少，同时完成原任务、守住必要边界。行数、层数和调用次数用于发现候选；取舍依据是责任与证据。

## 1. 先确定范围和不变量

读项目约定、需求、完整 diff 及相关调用方，用一句话写出本次改动要完成的用户任务，再列出不能退化的结果：输入输出、公开接口、数据语义、错误传播，以及相关的安全、完整性和恢复保证。

按用户请求确定工作方式：

- **评估、审查、出方案**：读取代码，在隔离副本中做必要实验，交付结论；正式源码保持原状。
- **精简、改造、落地**：继续实施有证据支持的最小改动。已有授权足够时直接完成，不反复请求确认。

默认范围是当前变更；用户明确指定模块或机制时，以该范围为准：

- 未提交工作：查看 `git status --short` 和 `git diff HEAD`，覆盖暂存与未暂存改动；未追踪文件按任务归属纳入。
- PR 或分支：确认实际目标分支，用 `git merge-base HEAD <target>` 确定基点，再审查基点到 `HEAD` 的差异。另有工作区改动时，单独记录归属，避免混入实验。
- 明确指定提交、目录或机制：沿其调用与数据路径确认边界，只触及完成本次消融所需的代码。

目标或比较基点无法从上下文确定时，先澄清这一项。记录已有改动，建立能只撤销自己实验的恢复方式；保留用户原有工作。范围外发现只报告，不顺手修复；提交、部署和数据迁移遵循当前授权。

**完成条件：** 用户任务、不变量、比较范围和实施权限均已明确。

## 2. 建立可比较的基线

从仓库配置找到适用的测试、类型检查、lint 或构建命令，先运行与候选相关的检查，记录已有失败和环境限制。后续只把新增退化归因于实验。

选择能代表原任务的正常输入，以及候选所承担责任对应的边界或失败输入。实验前后保持输入、环境、配置一致；涉及随机性或性能时，控制种子、负载和测量条件。

只采集与问题相关的成本，例如耗时、内存、请求次数、模型调用费用、依赖数量或重复维护点。结构变化与运行成本分开记录：代码变短本身不能证明更快或更便宜。

**完成条件：** 已有可复现的比较方法，并知道它覆盖和未覆盖哪些责任。

## 3. 按责任盘点候选

在约定范围内，逐项盘点函数、参数、分支、类型、模块、依赖、状态、注释与测试。审查 diff 时检查新增或修改部分；用户显式指定模块或机制时，覆盖该范围内承担相关责任的现有实现。每个候选先回答：**它负责什么？拿掉后，哪个具体场景可能受影响？**

| 候选 | 优先尝试 | 保留的依据 |
|---|---|---|
| helper、包装层、单独模块 | 内联、直接调用底层、并入消费者 | 名称解释重要步骤，或隔离真实复杂度、独立责任与稳定边界；单次调用也可能合理 |
| 参数、配置、泛型、手写类型 | 固定唯一内部取值，复用现有或推导类型 | 现有消费者需要差异，或公开契约、类型约束会受影响；仓库内没搜到调用不等于没有外部消费者 |
| guard、分支、fallback、try/catch | 移除或缩窄，观察对应输入与故障 | 真实可达场景需要它；类型声明本身不能证明外部输入已被验证 |
| 重复逻辑、多份数据、派生状态 | 搜索现有实现，统一规则或直接计算 | 平台、接口、时序、生命周期或性能需求存在必要差异 |
| 缓存、重试、复核层、转换链、依赖 | 绕过一层，或用已有能力替换 | 实测收益或必要保障足以抵偿引入的状态、维护和运行成本 |
| 注释、测试、格式变动 | 删除叙述性噪声、重复覆盖及无关变动 | 注释解释约束或取舍；测试保护独有行为或回归，不能只按行数判断 |
| 旧函数、入口、路由、兼容配置 | 查消费者与契约，尝试退役 | 仍有实际消费者、迁移责任或兼容承诺 |

优先处理无实际用途的扩展点、重复实现、无收益的间接层，以及脱离原任务的改动。保留适用范围内的一般规则；将现有特例改成通用规则时，也必须服务原任务，不能借机新增框架、选项或平台支持。

检查改动是否只在调用处补症状，例如按报告中的名称、路径或数值叠加特例；沿调用与数据流追查产生问题的规则。能在既定行为与范围内处理根因时，优先用针对根因的实现替代症状补丁；根因超出范围时，记录证据与后续建议。

函数承担多个无关职责时，可在本次范围内按职责局部拆分，让每段承担清晰责任。以降低理解成本为依据，保持行为与公开接口，避免为了缩短函数新增无收益的层次。

**完成条件：** 每个候选都有原责任和可执行的消融假设，而不只是“看着多余”。

## 4. 一次验证一个机制

按下面的循环执行，下一次实验从已接受的版本开始：

1. **提出假设。** 写清移除、内联、合并或替换什么，预期保持哪些结果、减少什么成本。存在连带关系的代码可以作为一个机制处理，例如包装函数与它独占的导入。
2. **做最小实验。** 只改变这一机制，沿用周边风格与命名。独立机制分开实验，避免一次删掉几层后无法判断因果。
3. **重跑同一验收。** 运行直接相关的检查与输入，比较行为和成本。检查未覆盖责任时，用最小针对性验证或明确的契约、调用路径证据补足。
4. **解释结果。** 检查失败先区分行为退化、环境问题与耦合实现细节的断言。行为退化证明该责任仍然需要，随后判断原实现还是更简单的实现能承担它。不能靠删掉行为测试、降低断言或改变期望来让实验通过。
5. **作出取舍。** 应用下表之一；实验不成立时，仅撤销本次实验，恢复到上一个已验证状态。

| 结论 | 依据与动作 |
|---|---|
| 删除 | 在声明的适用范围内，验收与责任均有证据覆盖，移除后没有必要行为退化；保留删除结果 |
| 合并 | 已核实语义相同，合并后必要差异仍被保留；运行各消费者的相关验收 |
| 替换 | 更简单的实现承担相同必要责任，比较结果支持取代；计入迁移成本 |
| 保留 | 机制有明确责任，实验显示移除会退化，或契约与调用路径证明其必要性；记录具体依据 |
| 待验证 | 缺少能作出判断的覆盖、环境或消费者信息；保持原状，写明缺什么证据 |

对安全、权限、数据完整性、并发和恢复机制，正常路径通过不足以支持删除；需要相应的失败、攻击、重复请求、竞争或恢复场景。无法验证时保留待验证结论。

删除测试要单独判断它保护了什么，以及剩余验证能否继续发现该回归；删除后的测试仍通过没有证明力。类似地，没有观察到机制收益，只能说明当前样本未观察到，不能直接推出它无用。

候选很多或实验跨多轮时，将每轮的假设、输入、检查结果和取舍保存为简短记录；一次小改动用交付表即可，无需额外建立文档体系。

**完成条件：** 每个候选已有带证据的取舍，或保持原状并明确标为待验证。

## 5. 收尾，检查退役与组合效果

对已接受的简化，沿引用和注册关系检查遗留函数、导入、路由、配置、依赖、测试与文档。只清理由本次改动造成的孤立项，以及已证实可退役的范围内旧路径。

涉及公开入口时检查消费者与兼容承诺；暂留兼容层要说明它服务谁，以及可验证的退出条件。保留仍然成立的使用文档，更新因本次改动失效的说明。

在最终组合上重跑基线任务和相关回归，并完成本次改动适用的类型检查、lint、构建等项目检查。即使单项实验通过，组合仍需确认。按同一范围比较前后 diff 和已选择的成本指标，再逐行复核剩余改动是否服务原任务。

**完成条件：** 最终组合已验证，自己引入的孤立项已清理，兼容责任和未验证项已说明。

## 交付

先说明保住了什么用户结果，再用简短表格给出主要取舍：

| 候选与原责任 | 动作 | 行为证据 | 成本变化或结构变化 |
|---|---|---|---|

随后列出实际执行的检查与结果、范围一致的 diff 前后统计（如 `git diff --stat`）、旧路径退役情况，以及待验证项或范围外发现。纳入范围的未跟踪文件须单独计入，`git diff --stat` 本身不会包含它们。仅评估时报告建议和实验结果，不虚构正式改动。

只报告实际测得的收益；未测量就写未测量。结论限定在已验证的输入、平台和条件内，不宣称所有历史行为等价，也不以“更优雅”代替证据。没有候选值得删除时，保留现状也是有效结果。
