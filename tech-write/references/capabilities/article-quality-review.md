# 文章质量五维自评与改进框架

## R — 原文

> "这个对于洞见的指导性框架，包括以下几个部分：1. 写作文章的动机及思考 2. 洞见文章要解答的元问题 3. 优秀洞见的加分项 4. 文章的表面功夫 5. 文章写好还有最后一公里。"
> ——《如何评价一篇文章》（张凯峰）

> "开宗明义，使用总－分－总的结构，清晰的小标题，每个部分之间逻辑过渡流畅，结尾有力，这都是写作的基本功，却也是最容易被忽略的部分。"
> ——《如何评价一篇文章》（张凯峰）

## I — 自述

评价文章本质主观，没有统一标准——但可以在一个指导性框架里检查。五个维度，从里到外：

**① 动机与思考（门禁）**：文章是否源于能说服自己的真实经历与情绪？有没有自己的独特思考？应付任务、自己都不信的内容在此止步。

**② 元问题**：文章回答了目标场景的哪个核心问题？任何媒体/平台都有它要回答的元问题（原书例：洞见的三元问题），文章至少命中其一。通用化：先弄清目标读者的核心关切，确认文章在回答它。

**③ 加分项**（非必需，但脱颖而出靠它）：争议性话题（价值在引发讨论、抛砖引玉，不是博眼球）；总结性经验（"N 个 XXX"式标题天然吸引关注收藏）；洞见性观点（独特视角、执拗语调、感同身受的情绪，区别于味同嚼蜡）；故事性描述（引人入胜胜过波澜不惊）。

**④ 表达与代入感**：目的型写作（招聘/销售/营销）把焦点放在读者身上——移情、挖掘痛点、用他们的语言、"做出来而不是告诉"（show, don't tell）；满篇"我们多好多聪明"是反模式。人称按功能选：第一人称陈述观点（参与者）、第二人称号召行动（对话感）、第三人称客观陈述（客户故事/新闻稿）。调性上，带自我怀疑的鲜活文字比"伟光正的不容置疑"更值得信赖。

**⑤ 结构**：除散文外，开宗明义、总-分-总、清晰小标题、部分间逻辑过渡流畅、结尾有力——基本功却最易被忽略。在获得读者信任之前，长套路与故弄玄虚是耍小聪明，会透支信赖。

## A1 — 应用示例（原书案例）

**案例（主编审稿实践）**：张凯峰给出的"N 个 XXX"标题示例——《企业实施 DevOps 的七大挑战》《DevOps 发展的 9 个趋势》《RESTful 架构风格下的 4 大常见安全问题》《敏捷实践 Showcase 的七宗罪》——是"总结性经验"加分项的原书样例。

**案例（调性示例）**：于晓强《软件无用论》——"回顾我自己这些年的技术生涯……所做过的技术决策，随着技术的革新，无一例外都是错误"，但依然"更好的保持开放心态、同时谨慎前行"。张凯峰评：这样的文字"比起伟光正的不容置疑，更有鲜活的特征，值得信赖"。

**案例（结构示例）**：《前端框架这么多，该何去何从？》——总（选择很多，该怎么选？）→分（选择需要考虑的维度）→总（总结优劣势，具体问题具体分析），是总-分-总的原书范例。

## A2 — 未来触发

**典型情境**：
1. 用户贴出一篇文章草稿："帮我看看怎么样/怎么改"
2. 用户问"这篇文章能发吗""还缺什么"
3. 用户感觉文章平淡但说不出哪里不对
4. 用户要给团队/媒体投稿，想先自评

**语言信号**：帮我看看这篇 / 评审 / 改稿 / 写得怎么样 / 能不能发 / review my article / how to improve this draft / is this good enough

**与相邻能力的区分**：还没动笔/只有选题 → article-positioning；已通过质量关、做发布前合规检查 → prepublish-check；只有排版问题 → chinese-tech-typography；表达看不懂的专项改进 → clear-expression。

## E — 执行步骤

**输入契约**：文章草稿或成品（必需）；目标发布渠道（可选，用于元问题维度）。文章缺失时请用户提供，不凭摘要评估。

1. **动机门禁**：问用户——这是你的真实经历/真实观点吗？文中独有的思考是什么？两项皆无则停止评估，建议补充亲历素材。完成标准：明确指出文章的"独特思考"所在段落，或确认缺失。
2. **元问题判定**：确认目标渠道（无则以"通用技术读者"为场景），说出本文回答的元问题/读者核心关切。完成标准：一句话指出命中的元问题；命中不了则标记为主要改进项。
3. **加分项扫描**：逐项检查四个加分项，并判断能否低成本获得（如改标题为总结式）。完成标准：列出"已有/可改造/不适用"三栏结论。
4. **表达检查**：统计主语——满篇"我们"且目的为吸引读者时标记焦点错位；检查人称使用与文章目标是否匹配；检查语气是否"伟光正"式不容置疑。完成标准：给出表达维度的具体修改建议（含改法示例）。
5. **结构检查**：是否开宗明义/总-分-总/小标题清晰/过渡流畅/结尾有力；有无故弄玄虚的长套路。完成标准：五要素逐项打勾或给改法。
6. **汇总改进清单**：按"必须改（①②不过）/建议改（③④⑤）"两档排序输出。完成标准：每条建议具体到段落与改法，用户可逐条执行。

**输出契约**：五维判定表（每维通过/不通过/不适用 + 证据）+ 分档改进动作清单。

## B — 边界

- 框架是"指导性"而非统一标准（原书元声明）：五维内允许自由腾挪，不要当成僵硬打分表；散文等体裁不适用结构维度。
- 加分项非必需：不为凑项强行制造争议或硬凑"N 个 XXX"，原书警告博取眼球不是目的。
- 元问题的原书实例为 Thoughtworks 语境，使用时抽象为"目标读者的核心关切"。
- 本卡不做发布合规判断（脱敏/版权）——那属于 prepublish-check；不做排版细节——那属于 chinese-tech-typography。
- "质量终将被认可"与"最满意文章无人问津"在原书中并存（两位作者张力）：评估质量时不承诺流量结果。
