# 清晰表达训练与写作编程共通原则

## R — 原文

> "我习惯把我正在叙述的对象，想象为一名刚入门的程序员，或者只是一名有少许编程背景的 QA 同学，甚至是完全没有背景的 HR。然后思考我应该如何通过最通俗易懂的表述，让他们理解我想表达的概念。"
> ——《写了十年技术博客的收获》（李光毅）

> "编写代码这件事其实是在同时与两个截然不同的听众对话：一个是编译器/解释器，另一个是你团队中其他的程序员，包括未来的你自己。……人类才是代码的终极听众。"
> ——《写作和编程》（董强译）

## I — 自述

"通俗易懂"不是天赋而是可代入的自测程序：写作时把叙述对象具象化为一个入门者——刚入门的程序员、稍懂编程的 QA、完全没背景的 HR——然后问自己：这个人能看懂吗？这能直接暴露表达转嫁：贴一大段代码加一句"自己去理解吧"，等于把词典扔给小学生让他自学语文，把本应由作者承担的解释成本甩给读者。正确做法是用最简单的文字引导和解释。

写作和编程共享一套表达纪律（原书借 Strunk & White《风格的要素》逐条映射）：
1. **设计先行**：动笔/动手前必须有认真考虑过的结构计划，尺度匹配——洗衣清单随手写，人物传记至少要有粗略方案；
2. **宁标准勿另类**：了解新词新范式但不被潮流带跑；
3. **去除多余**：段落不应有不必要的句子，句子不应有不必要的词——不是要求短，是要求每字每行都表达了本意；
4. **平行结构**：内容与功能相似的表述，外形也应相似，降低读者识别成本；
5. **不要肆意妄为**：想到什么写什么是意大利面条代码/文章的配方；
6. **自然但自检**：用顺手易用的词汇与 API 自然地写，但自然不构成免检理由；
7. **清楚明了是美德**：写作/编程是交流，交流以清晰为前提（但清晰不是唯一目标，允许风格差异）；
8. **不要解释过多**：写作节制副词，编程节制注释——让代码本身显现意图，注释只留代码无法表达的"为什么"。

统摄框架是"双听众模型"：代码/文章同时面向机器（编译器/搜索引擎）与人（团队、未来的自己），人类才是终极听众——可读性是第一维度，机器通过只是及格线。

## A1 — 应用示例（原书案例）

**案例（转述+演绎，董强译）**：原书把 Strunk & White 的写作格言做"全局替换"演绎——把 writing 替换为 programming 后，"一个段落不应含有不必要的句子，一个句子不应含有不必要的单词"变成"一个函数不应含有不必要的语句，一个语句不应含有不必要的表达式"，读起来"就像出自《代码大全》"。这个替换实验本身就是"写作与编程同构"的论证方式。

**案例（作者实践，李光毅）**：他反对"不分原由的把文档、代码、或者是《XX 权威指南》扔给某个人，然后让他自己去理解"，并以"把汉语词典递给小学生让他自学语文"作比——可以，但很难，也完全没有必要。

## A2 — 未来触发

**典型情境**：
1. 用户写的技术文章/文档被反馈"看不懂"
2. 用户想把一个复杂概念讲给非专家（新人、产品、HR）
3. 用户问代码注释/变量命名/README 怎么写才好
4. 用户文章堆了很多代码块，读者流失

**语言信号**：看不懂 / 讲不明白 / 通俗解释 / 表达不清 / 代码注释 / too hard to understand / explain like I'm a beginner / make it clearer / ELI5

**与相邻能力的区分**：整篇文章的五维质量评估 → article-quality-review；排版视觉规范 → chinese-tech-typography；学习内化检验 → writing-driven-learning。

## E — 执行步骤

**输入契约**：待改进的文本（文章/段落/文档/注释，必需）；目标读者背景（缺失时先询问或默认"刚入门的同行"）。

1. **设定想象读者**：与读者确认一个具体的低背景人设（入门程序员/QA/HR）。完成标准：一句话描述此人知道什么、不知道什么。
2. **转嫁扫描**：找出文本中所有"解释成本转嫁"——未解释的大段代码、"详见文档/源码"、未定义的术语缩写。完成标准：列出转嫁点清单。
3. **逐点改写**：每个转嫁点改为引导式解释（先结论、再类比、后细节）。完成标准：想象读者人设读完不需查外部资料即可复述大意。
4. **原则过检**：按八原则逐条检查——结构有无预先设计/有无追潮流式炫技/逐句问"这句表达了本意吗"/相似内容结构是否平行/顺序是否有逻辑非兴致/语言自然但不免检/是否清晰/注释是否只留"为什么"。完成标准：每条原则给出"通过/修改了什么"的记录。
5. **复读验证**：以想象读者身份通读一遍。完成标准：没有需要回读两次以上的句子。

**输出契约**：改写稿 + 转嫁点清单 + 八原则检查记录。

## B — 边界

- 《写作和编程》是转译文章，原则是 Strunk & White 的映射，非原生方法论；引用时注明出处。
- "少用注释"与"不做解释"是一对边界，方向相反而已：反对的是用注释复述代码（这是什么），也反对不解释的代码块（读者看不懂）。注释保留"为什么"，正文承担"是什么"。
- 清晰是美德不是铁律：原书明确承认风格多样性，诗歌/文学化写作不适用本卡。
- 想象读者法不适用于专家间通信（如论文、RFC）——那时"入门者人设"会造成过度解释。
- 刻意练习警告：重复低水平输出（天天 hello world）不产生长进，每次写作须比上次更清楚一点才算训练。
