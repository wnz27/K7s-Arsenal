# 写作工具链：纯文本、版本管理与资产同步

## R — 原文

> "平衡了利弊后选择以 Markdown 作为初稿的编辑工具。……单一 Markdown 文件就非常利于管理：方便预览整书情况；方便章节之间相互引用；方便导出。……增强的 Markdown 语法中可以直接引用代码。这样我更改了代码以后，书中的代码也更新了，避免了不同步的问题。"
> ——《用什么工具写书》（贺思聪）

## I — 自述

工具选型的第一标准是"减少工具对写作的负担"（录入、调格式的干扰），第二是可版本管理。三方权衡：Word（易上手、所见即所得，但难做版本管理）；Markdown（纯文本、可视化工具丰富、程序员友好、天然适配 Git）；Latex（专业，但学习与配置成本高）。结论：初稿用 Markdown，内容与排版分离——排版后置，成稿后再转 Word 交编辑。

反直觉实践：30 万字的整书用单一 Markdown 文件管理，而不是一章一个文件。收益三条：随时预览整书结构与篇幅、章节互引无需跨文件链接、整书一次性导出。

资产同步（SSOT，单一事实来源）：书中代码示例通过增强语法直接引用源代码文件——代码一改，书中引用随之更新，杜绝手工复制造成的书稿与源码不同步；流程图用 graphviz 等"图即代码"工具，图像像代码一样进版本库。配图专业化不靠复杂工具，靠四个设计元素：字形字体（大小粗细变化）、颜色（基本配色理论）、层次（尺寸/位置/深浅）、阴影。整书从头到尾用 Git 管理——所有产出物可 diff、可回滚、可追溯。

## A1 — 应用示例（原书案例）

**案例（反例，邱俊涛亲历）**：实体书出版时，出版社要求 Word/WPS 格式，他的 Markdown 稿转 Word 后跨平台（Mac→Windows）排版变样，"字符集、字体、版本差异导致印刷与原稿出入大"——内容与排版未分离的真实事故。

**案例（工程实录，贺思聪亲历）**：30 万字书稿单一 Markdown 文件 + VS Code + Markdown Preview Enhanced 插件（自动预览、自动目录、内嵌图片与代码、导出 Word/PDF）+ Git 全程管理——"整本书从头到尾都是用 Git 管理的，这也是程序员标准的工具"。

## A2 — 未来触发

**典型情境**：
1. 用户要写技术书/长文档，问用什么工具怎么管理
2. 用户的书稿/文档中代码示例与真实代码不同步
3. 用户问 Markdown 写作的工程化实践（版本控制、协作）
4. 用户在 Word/Markdown/Latex 之间纠结

**语言信号**：写作工具 / Markdown / 版本管理 / 代码同步 / 书稿管理 / writing tools / markdown workflow / version control for docs / keep code samples in sync

**与相邻能力的区分**：写书的整体方法论（迭代/试读/决策）→ book-writing-engineering；排版规范检查 → chinese-tech-typography；单篇文章流程 → drafting-workflow。

## E — 执行步骤

**输入契约**：写作项目类型（书/长文档/系列文章，必需）；技术栈与协作人数（影响工具选择）。

1. **选型决策**：按"最小化写作干扰 + 可版本管理"评估候选工具。完成标准：一句话选型结论 + 放弃项理由；用户坚持 Word 时尊重但提示版本管理风险。
2. **工程骨架**：建立单文件书稿（或按项目规模说明取舍）+ Git 仓库 + 目录约定（正文/代码/图）。完成标准：仓库可 clone 即预览。
3. **代码同步**：配置引用机制（Markdown 增强语法/include 类插件/静态站点生成器的代码引入），让书中代码直接引用源文件。完成标准：改一处源文件代码，预览中同步更新——必须实际验证。
4. **图资产**：流程图用"图即代码"工具（graphviz/Mermaid 等）入库；截图按四元素（字形/颜色/层次/阴影）做专业化调整。完成标准：图源文件入库，重新生成可复现。
5. **导出与交接**：配置导出通道（PDF/Word/HTML），排版后置。完成标准：一键导出；交接格式符合对方（编辑/出版社）要求。

**输出契约**：可用的书稿工程（仓库结构 + 同步机制验证记录 + 导出通道）。

## B — 边界

- 具体工具与插件为 2020 年版本（Markdown Preview Enhanced、gitbook 等）：按当下等价物替换，原则（纯文本优先、SSOT、版本管理、内容排版分离）长效。
- 单一文件法依赖纯文本 + 版本管理工作流；多人并行写同一文件时冲突成本上升，原书未覆盖分支策略——多人协作场景建议按章拆分或约定编辑窗口，如实告知这是原书空白。
- graphviz 类工具学习成本本身也是"工具负担"：图量小时直接用截屏/手绘工具不违背原则。
- 本卡不评价内容质量；工具配置不应成为拖延写作的借口（原则 1 就是减少工具干扰）。
